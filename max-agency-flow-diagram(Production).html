🤖 Max Agency

The autonomous developer agency you set up once — then it plans, codes, reviews, and ships by itself.

🏗️ How It Works — The Three Parts
Max Agency runs across three places that talk to each other automatically.

🐍 Hermes (Linux Brain)

Runs inside WSL on your Windows machine. Wakes up every 5 minutes via systemd timers. Handles all the invisible coordination work.

  • Orchestrator: dispatches tasks, routes verdicts
  • Coder: implements what the Architect planned
  • Writes to GitHub on every tick
  • Escalates to your phone when it needs you

🐙 GitHub (The Bulletin Board)

Every task is a GitHub Issue. Every piece of code is a Pull Request. Labels route tasks between agents. Nothing is stored in memory.

  • Issues = tasks in the queue
  • Labels = which AI picks it up
  • PRs = code ready for review
  • Comments = verdicts and status

🧠 Claude Code (Windows Brain)

Runs as a silent Windows Scheduled Task every 5 minutes. Uses the most capable Claude models for the high-stakes roles.

  • Architect: turns your goal into a plan
  • CTO: reviews code before it merges
  • Uses GPT-4o / Claude Opus for reasoning
  • Runs completely in the background
📋 Installation — Step by Step
Six steps. You only do this once. Orange text = something you must change to match your own setup.
⚠️ Before you begin: Everywhere you see <text-like-this> in a command, replace it with your own value. The examples below each code block show you exactly what a filled-in command looks like.

Push the Max Agency repo to your GitHub

Max Agency is a template — you host your own copy on GitHub so Hermes can pull the latest config whenever it starts. Run these commands from your Windows Terminal (or PowerShell) in the Max Agency folder.

📂 Open a terminal and navigate to the Max Agency folder
cd <path-to-Max_Agency>
git init -b main
git remote add origin https://github.com/<your-username>/Max_Agency.git
git add .
git commit -m "initial: max agency baseline"
git push -u origin main
📌 Example (fill in your own values):
cd C:\Users\Alice\Max_Agency
git remote add origin https://github.com/alice123/Max_Agency.git
💡 Tip: Create the empty GitHub repo first at github.com/new — name it Max_Agency, keep it private, and don't add a README (you're pushing one already).

Create your project repo and set up labels

This is the repo Max Agency will actually build software in. It's separate from the Max Agency repo — think of Max Agency as the engine, and your project repo as the car it's building.

🐙 Run in PowerShell (Windows Terminal)
# Create the repo on GitHub
gh repo create <your-username>/<your-project-repo> --private

# Set up the labels Max Agency uses to route tasks
cd <path-to-Max_Agency>
.\scripts\setup-project.ps1 -Repo "<your-username>/<your-project-repo>"
📌 Example:
gh repo create alice123/my-saas-app --private
.\scripts\setup-project.ps1 -Repo "alice123/my-saas-app"
⚠️ Important: Remember this exact repo slug (your-username/your-project-repo) — you'll use it in Steps 3 and 5 too. It must match exactly, including capitalisation.

Bootstrap Hermes (the Linux brain)

Hermes needs to know about your project repo and create the right profile files. You do this by pasting three special prompts into a Hermes chat session in WSL. Think of it as a one-time onboarding conversation.

🐧 Open a WSL terminal and start Hermes
hermes chat

Then paste these three prompts in order, waiting for each to complete before pasting the next:

Prompt H1 — copies profile files (paste this first)
See Human_Runbook.md → Section H1 for the full prompt text. It sets up the orchestrator and coder profiles.
Prompt H2 — registers your project repo (paste this second)
# The VERY FIRST LINE of H2 must match your project repo:
export PROJECT_REPO="<your-username>/<your-project-repo>"
# Then paste the rest of H2 from Human_Runbook.md → Section H2
📌 Example first line of H2:
export PROJECT_REPO="alice123/my-saas-app"
Prompt H3 — verifies the setup (paste this third)
See Human_Runbook.md → Section H3. It runs 8 checks and prints BOOTSTRAP_COMPLETE when everything is correct.
💡 Tip: The full H1, H2, and H3 prompts are long copy-paste blocks in Human_Runbook.md. Don't write them by hand — copy them exactly.

Deploy the systemd timers (the Hermes heartbeat)

Hermes runs on systemd timers — two background services that fire every 5 minutes. Without this step, Hermes is installed but sleeping. This pulls the latest config from GitHub and activates the timers.

🐧 Run in WSL terminal
git -C ~/.hermes-cache/Max_Agency pull --rebase
bash ~/.hermes-cache/Max_Agency/hermes-config/deploy.sh
💡 What this does: Copies the profile configs and service files into the right places, then tells systemd to reload. After this, run systemctl --user list-timers in WSL — you should see hermes-orchestrator-tick.timer and hermes-coder-tick.timer with a "NEXT" time showing.
⚠️ Re-run this step any time you pull an update to Max Agency. It's safe to run as many times as you want.

Register the Windows Claude Code routine

This creates a Windows Scheduled Task that runs Claude Code silently in the background every 5 minutes, checking GitHub for any CTO review or Architect work that needs the Windows AI brain.

🪟 Run in PowerShell (Windows Terminal) — as your normal user, not Admin
cd "<path-to-Max_Agency>\claude-code-routine"

.\register-task.ps1 `
  -Repo "<your-username>/<your-project-repo>" `
  -ProjectPath "<path-to-Max_Agency>"
📌 Example:
cd "C:\Users\Alice\Max_Agency\claude-code-routine"
.\register-task.ps1 -Repo "alice123/my-saas-app" -ProjectPath "C:\Users\Alice\Max_Agency"
⚠️ The repo slug here must exactly match what you used in Step 3. If they differ, the Windows brain and the Linux brain will be managing different repos and nothing will connect.
💡 Verify it worked: Open Windows Task Scheduler (search for it in the Start menu) → look for MaxAgency-ClaudeCodeRoutine. It should say "Ready" with a next run time. Or check the log: Max_Agency\logs\claude-routine.log — after 5 minutes you should see a TICK entry.

Fire the first kickoff — tell the Architect what to build

Everything is running. Now you give the system its first goal. Open Claude Desktop, start a new conversation, and paste the Architect kickoff prompt from the runbook — then describe what you want to build.

🧠 Open Claude Desktop → New Conversation
Paste the Architect Kickoff Prompt from Human_Runbook.md → Section "Architect kickoff"

Then add your project brief, for example:
"Build a simple web app that lets users track their daily habits. Users can add habits, check them off each day, and see a streak count."
💡 What happens next: The Architect asks you up to 5 clarifying questions, writes a PLAN.md, submits it to the CTO for review, then creates a kickoff GitHub issue. The Orchestrator (Hermes) picks up that issue on its next tick and creates all the task issues. From there — it runs itself. 🎉
🚀 Starting a New Project
Already set up Max Agency? Starting a second (or third) project is just 4 steps — no reinstalling anything.

Create the new project repo on GitHub

gh repo create <your-username>/<new-project-repo> --private — then run .\scripts\setup-project.ps1 -Repo "<your-username>/<new-project-repo>" to create all the labels.

Re-run H2 in Hermes with the new repo slug

Open WSL → hermes chat → paste H2 with the first line changed to export PROJECT_REPO="your-username/new-project-repo". This updates ~/.hermes/.env so the Linux brain targets the new repo.

Re-register the Windows Claude Code routine

Run .\register-task.ps1 -Repo "<your-username>/<new-project-repo>" -ProjectPath "<path-to-Max_Agency>" — the -Force flag is built-in, so it overwrites the old registration safely.

Paste the Architect kickoff prompt

Open Claude Desktop → new conversation → paste the Architect kickoff prompt → describe what you want to build. The agency takes it from there.

⚙️ How Every Task Gets Done
Once started, this loop runs automatically, 24/7, every 5 minutes.
1

🎯 You Set the Goal

Paste a brief to the Architect. It writes PLAN.md and creates task issues on GitHub.

→
2

📋 Orchestrator Queues Tasks

Reads PLAN.md, creates GitHub issues with labels, promotes them through the queue: backlog → ready → in-progress.

→
3

💻 Coder Implements

Picks up an in-progress issue, writes the code on a branch, opens a Pull Request, labels the issue "review".

→
4

🔍 CTO Reviews

Reads the PR diff, checks every acceptance criterion. Posts APPROVED or CHANGES REQUIRED.

→
5

🚦 Orchestrator Routes

APPROVED + no human needed → auto-merges. CHANGES REQUIRED → bounces back to coder. Needs your eyes → messages you.

→
6

✅ Shipped

PR merged, issue closed, next task dispatched. Repeat until the plan is done.

🔄 CHANGES REQUIRED → Auto-Retry: If the CTO rejects the code, the verdict is automatically pasted onto the task issue and the coder picks it up again on the next tick. The loop runs up to 2 rounds before the CTO escalates to you.
🎭 The Five AI Roles
Each role has exactly one job. They never step on each other's work.
Windows (Claude Code)

🏛️ Architect

Turns your one-paragraph goal into a complete, machine-executable PLAN.md. Asks you up to 5 clarifying questions first, then hands the plan to the CTO for sign-off before any code is written.

WSL / Hermes

🎼 Orchestrator

The conductor. Reads PLAN.md, creates task issues, promotes them through the queue, dispatches them to the right AI, and routes CTO verdicts (auto-merge, bounce-back, or escalate).

WSL / Hermes

💻 Coder

Implements the task. Creates a branch, writes the code, commits, pushes, opens a PR, and labels the issue "review". Never merges its own work — that goes to the CTO.

Windows (Claude Code)

🔍 CTO

Independent quality gate. Reads the PR diff against the acceptance criteria. Posts APPROVED (auto-merge if safe), CHANGES REQUIRED (bounce back), or ESCALATE (needs your eyes). Never touches the code itself.

Fully Automatic

⚙️ Mechanics Script

A deterministic bash+Python script that runs before every Orchestrator tick. Handles heartbeat, git pull, queue promotion, dispatch, stale reclaim, PR tracking, and verdict routing — no AI judgment needed.

🛡️ Why the CTO is separate from the Coder: The CTO and Coder run on completely different AI instances and have read each other's code. The CTO has no incentive to approve bad work — it's structurally independent. This prevents the AI from approving its own mistakes.
👤 What You Actually Do Day-to-Day
Mostly nothing. Max Agency is designed to run without you. Here's when it does need you:
📱

Reply to Telegram messages (the merge-approval flow)

When the CTO flags a change as "needs human eyes" (UI changes, database changes, anything irreversible), it sends you a Telegram message with a link to the PR. Reply with 1 = merge, 2 = reject, or 3 = explain. If you don't have Telegram set up, the message goes to a log file — check ~/.hermes/profiles/orchestrator/escalations.log in WSL.

👀

Review the Architect's plan before work starts

After the Architect and CTO agree on a plan, the Architect shows you PLAN.md and waits for a thumbs-up before creating any task issues. This is your one chance to redirect the project before AI effort is spent. It's a one-word reply: "Approved" or "Change X."

🚨

Handle escalations (rare)

If the CTO rejects a task 2 times in a row and still can't approve it, or if the Architect can't figure out what you want, you'll get an escalation. It'll tell you exactly what's blocking progress and ask for a decision. These should be rare — usually less than one per project.

🔧 Troubleshooting — Quick Reference
Something not moving? Start here before reading the full runbook.
Symptom Most Likely Cause Fix
Nothing happening after setup Systemd timers not active In WSL, run: systemctl --user list-timers — both hermes-orchestrator-tick.timer and hermes-coder-tick.timer should show a "NEXT" time. If not, re-run deploy.sh (Step 4).
Windows log only shows "NO_WORK" every 5 min Repo slug mismatch between Windows and WSL Check that ~/.hermes/.env in WSL has PROJECT_REPO=your-username/your-repo and that register-task.ps1 was run with the same slug. They must be identical.
CTO verdict posted but PR wasn't merged Orchestrator hasn't ticked yet since verdict Run mechanics manually in WSL: PROJECT_REPO=owner/repo bash ~/.hermes/profiles/orchestrator/orchestrator-mechanics.sh
CTO review issue sitting open with no verdict Windows Claude Code missed the tick (process was already running) Check Max_Agency\logs\claude-routine.log — look for the tick that matches the issue number. If missing, wait for the next 5-min tick or re-run run-tick.ps1 manually.
Task stays "in-progress" forever with no branch Coder timed out or crashed; stale claim The Orchestrator will auto-reclaim it within 60 minutes and re-dispatch. To reclaim immediately, run the mechanics script manually.
Architect keeps asking questions I've already answered New Claude Code session, no memory of prior chat Paste your previous answers again, or include them in the kickoff brief. Claude Code has no memory between sessions — the brief must be self-contained.

📖 Acronyms & Terms Explained
PRPull Request — a bundle of code changes waiting for review before merging into the main codebase
CIContinuous Integration — automated tests that run every time code is pushed (not required for Max Agency, but supported)
WSLWindows Subsystem for Linux — runs a real Linux environment inside Windows, used by Hermes
HermesThe Linux AI gateway that runs the Orchestrator and Coder as isolated profiles inside WSL
systemdLinux service manager — runs the Hermes timers in the background every 5 minutes
LabelA tag on a GitHub Issue that routes it to the right AI (e.g., assigned:claude-opus → Windows brain picks it up)
TickOne 5-minute cycle of the Orchestrator or Claude Code routine checking GitHub and doing its job
KickoffA special GitHub Issue (labeled kickoff) that tells the Orchestrator to read PLAN.md and create all task issues
CTO ReviewA GitHub Issue created by the Orchestrator for Claude Code to review a PR. Different from the PR itself.
PLAN.mdThe Architect's output — a markdown file with phases, tasks, dependencies, and rollback instructions for the whole project
VerdictThe CTO's decision on a PR: APPROVED (merge it), CHANGES REQUIRED (fix and resubmit), or ESCALATE (needs a human)
ghThe GitHub CLI — a command-line tool both AIs use to read and write GitHub issues, PRs, and comments
